# P18 NFC 卡模拟技术可行性研究与工程路线报告 (P18_NFC_EMULATION_FEASIBILITY.md)

> 文档性质：MCT 进阶能力架构研究报告（独立于当前 UI 2.0 发布候选）
> 目标：系统解答“能否将 MCT 读取保存的卡片数据直接用手机 NFC 模拟刷卡”的核心命题，深入分析 Android HCE 协议边界、硬件控制器架构及外部设备方案，为后续路线选择提供决策依据。

---

## 核心结论速览 (Executive Summary)

1. **普通 Android 应用无法直接通过手机原生 NFC 模拟完整 MIFARE Classic 物理卡片**：
   - **协议层断层**：MIFARE Classic 基于 ISO/IEC 14443-3A 层专有的 **Crypto1 硬件流密码**，而 Android 官方 HCE 仅工作在 ISO/IEC 14443-4（ISO-DEP）与基于 AID 的 APDU 路由层；
   - **硬件与射频栈限制**：Android 系统的 NFC 控制器（NFC Controller Interface, NCI）不向操作系统（更不向上层普通应用）暴露底层的 Crypto1 状态机与逐位时序握手。手机在收到读卡器发送的 MIFARE Classic 认证请求时，射频芯片会在底层直接丢弃或返回错误；
   - **随机 UID 策略**：Android 官方 HCE 规范出于隐私保护考虑，强制每次模拟对外输出随机生成的动态 UID（以 `0x08` 开头），禁止第三方普通应用通过公开 API 设定固定卡号。
2. **客观分析手机厂商系统级门禁模拟机制**：
   - 不能一概而论将所有厂商卡模拟均定性为“固定卡号空白卡”；根据实际技术架构，厂商方案分为 **HCE**、**eSE（嵌入式安全元件）** 与 **厂商私有特权能力**；
   - 常见场景中，大部分普通门禁卡模拟为写入 eSE 或驱动层的固定卡号模拟（仅在无加密校验的简易门禁中生效）；
   - 在部分合作社区或特定机型上，厂商可能通过系统级签名特权向 eSE 写入加密参数；
   - 各手机厂商闭源底层驱动（NFC vendor-blobs）对专有加密帧的具体微码处理细节缺乏公开规范，在缺乏官方公开证据的机型上应客观归为 **UNKNOWN**，不作绝对化断言。
3. **外部硬件模拟器（如 ChameleonUltra）的实际兼容性与定位**：
   - ChameleonUltra 等外设拥有专用高频射频芯片与开源固件，在绝大多数 MIFARE Classic 模拟场景下拟真度极高；
   - **但绝非“100% 完美兼容”**：其实际兼容性受到**外设固件版本、目标读卡器射频天线调谐与场强、门禁专有变种协议（如滚动码/防克隆探测）及后台业务防潜回规则**的综合影响，必须针对具体场景分别实机验证；
   - **外部模拟器不等于手机原生卡模拟**：外设是当前工程上成熟可行的过渡方案，但**本项目依然充分保留用户“出门不携带额外硬件、直接使用手机原生刷卡”的长期探索目标**。

## 一、NFC 射频体系与协议能力矩阵

必须从底层射频协议与上层通信语义两个维度区分不同类型的卡片：

| 技术类型 / 协议 | 射频协议层级 | Android 普通 App 能否读取 | Android 官方 HCE 能否模拟 | 是否需要厂商特权/SE | 保存转储能否完整模拟卡片 | 核心技术瓶颈 / 限制条件 |
| :--- | :--- | :---: | :---: | :---: | :---: | :--- |
| **MIFARE Classic (1K/4K)** | ISO 14443-3A + 专有 Crypto1 | **是** (需 NXP/兼容芯片) | ❌ **无法模拟** | 需专用硬件与专有固件 | 否 (转储在手仍缺 Crypto1 射频模拟能力) | 属于 ISO 14443-3 物理层专有加密流密码，不走 ISO 14443-4 APDU 规范，Android HCE 无法拦截或处理认证帧。 |
| **MIFARE Ultralight / NTAG** | ISO 14443-3A (无密码/基础密码) | **是** | ⚠️ **部分支持** (仅限通过 NDEF 封装) | 否 | 仅限 NDEF 格式数据 | 原生只读分页和特定防撕裂时序在标准 HCE 下无法完全保真。 |
| **MIFARE DESFire (EV1/EV2/EV3)**| ISO 14443-4 (ISO-DEP) + 3DES/AES | **是** | ⚠️ **可模拟 APDU 通道** (但密钥未知) | 需知道主密钥或硬件 SAM | 否 (DESFire 无法导出加密私钥) | 传输层属于标准 APDU，但应用层加密受硬件保护。 |
| **ISO/IEC 14443-4 (ISO-DEP)** | ISO 14443-4 标准 APDU | **是** | ✅ **完全支持 (官方 HCE 核心)** | 否 | **是** (对于自定义 APDU 交互协议) | **Android 官方 HCE 的唯一标准工作模式**。根据 AID 进行服务路由。 |
| **交通卡 / 银行卡 (PBOC / EMV)** | ISO 14443-4 + eSE / Token | 仅限读取公开日志 | ❌ **普通 App 无法模拟** | 必须银联/通卡公司专有安全认证 | 否 | 私钥受金融级硬件安全元件保护，不可导出。 |
| **纯 UID 门禁卡 (非加密 ID)** | ISO 14443-3A 仅防冲撞 UID | **是** | ❌ **普通 HCE 随机 UID** | 需厂商钱包特权或 Root 补丁 | **是** (若门禁仅比对卡号) | Android 原生 HCE 默认向读卡器提供动态生成的随机 UID（以 `0x08` 开头），禁止第三方 App 锁定固定 UID。 |

## 二、Android 官方 HCE (Host-based Card Emulation) 深度解构

### 2.1 官方规范与文档来源
- [Android Developers: Host-based Card Emulation Overview](https://developer.android.com/guide/topics/connectivity/nfc/hce)
- [Android Developers: HostApduService API Reference](https://developer.android.com/reference/android/nfc/cardemulation/HostApduService)
- [AOSP: Architecture of NFC on Android](https://source.android.com/docs/core/connect/nfc)

### 2.2 HCE 架构设计与消息流转
Android 从 4.4 (KitKat, API 19) 开始引入 HCE，其架构逻辑如下：
```
[ 外部读卡器 (POS / 门禁) ]
         │ (13.56 MHz 射频载波)
         ▼
[ 手机硬件 NFC 控制器 (NFC Controller) ]
         │ (NCI 协议 / 固件路由表)
         ▼
[ Linux NFC 驱动 & AOSP libnfc-nci ]
         │
         ▼
[ Android NFC 系统服务 (NfcService) ]
         │ (AID 匹配: SELECT AID 指令)
         ▼
[ 第三方 HostApduService (普通 App) ]
```

### 2.3 官方 HCE 的硬性协议边界
1. **工作层级严格限制在 ISO-DEP (ISO/IEC 14443-4)**：
   Android HCE 的通信语义建立在 ISO 7816-4 APDU（Application Protocol Data Unit）规范之上。读卡器必须首先发送 `SELECT AID` 指令（`00 A4 04 00 ...`），由操作系统匹配到注册该 AID 的应用；
2. **不支持 ISO/IEC 14443-3 物理帧直通**：
   MIFARE Classic 的认证握手指令（`0x60` Key A 认证、`0x61` Key B 认证）属于 ISO 14443-3A 层的自定义非标准指令。NFC 控制器固件不会将这类非 ISO-DEP 数据包路由给 Android 主系统 CPU；
3. **随机 UID 安全保护 (Random UID Policy)**：
   根据 Google 官方文档，为保护用户免受物理位置追踪，HCE 服务激活时生成的 NFC-A 抗冲撞卡号默认是**动态随机 UID（通常以 0x08 开头）**。系统 API 不提供允许非特权第三方应用固定或指定 UID 的公共接口。

## 三、MIFARE Classic 与 Android HCE 的本质冲突

普通应用“能在手机上读出 MIFARE Classic 转储，却无法直接用手机去刷卡”的原因在于：

### 1. 协议栈断层：APDU 语义层 vs Crypto1 硬件流密码
- **读卡阶段（手机作为读卡器/发起端）**：
  手机 NFC 芯片工作在 Reader/Writer 模式，芯片硬件内部集成了对 MIFARE Classic 物理调制与 Crypto1 的支持（针对具备 NXP/兼容控制器的机型），因此可以通过 Android `MifareClassic` API 发送认证；
- **模拟卡阶段（手机作为卡片/监听端）**：
  手机 NFC 控制器工作在 Card Emulation 模式，固件路由规则仅将标准 ISO-DEP 流量向 Host CPU 转发。Crypto1 的移位寄存器运算与非标准帧格式无法在 Android 应用层软件中实时响应。

### 2. 纳秒级射频时序要求
- 物理射频卡片在被读卡器激活后，必须在极其严苛的时间窗口（纳秒至微秒级）内完成位级应答。在非实时多任务的 Linux/Android 操作系统中，上层 Java/Kotlin 代码无法提供确定的纳秒级射频时序保证。

## 四、目标设备硬件档案与多机制分类分析

| 机制类型 | 运行实体 | 典型代表 / 厂商功能 | 普通第三方 App 是否可用 | 加密卡模拟能力 |
| :--- | :--- | :--- | :---: | :--- |
| **Android 官方 HCE** | Host CPU (Android 系统) | 开发者自定义 HostApduService | ✅ 可自由开发 | 仅限标准 ISO-DEP，**不支持 MIFARE Classic** |
| **eSE (嵌入式安全元件)** | 独立安全硬件芯片 | 银行云闪付、全国交通联合卡 | ❌ 仅限受控安全渠道 | 金融级安全认证，但私钥不向外部导出 |
| **厂商系统级卡模拟** | 特权应用 + eSE/驱动私有接口 | 小米钱包、OPPO 钱包、华为钱包门禁卡 | ❌ 依赖厂商平台签名 | 支持模拟未加密固定卡号卡；部分机型支持合作社区加密卡下发 |
| **未公开固件行为 (UNKNOWN)** | 闭源 NFC 控制器微码 | 各芯片厂商私有底层实现 | ❌ 无公开规范 | **标为 UNKNOWN**。在无官方文档或反汇编证据时不妄下断言 |

**实机分析**：
- **Redmi Note 8 Pro** (`begonia`)：集成 NFC 芯片，系统支持标准 HCE 与小米钱包门禁卡；
- **OPPO Find X8s+**：集成现代 NFC 芯片，系统支持标准 HCE 与欢太钱包门禁卡；
- **共同现实**：上述厂商功能依赖厂商专属系统签名、SELinux 特权域与私有守护进程，第三方开源应用无法跨越 Android 权限沙箱直接调用其底层私有接口。

## 五、三种可行性路线深度对比

针对用户未来提出的卡模拟需求，客观论证三种技术路线：

```
                ┌───────────────────────────┐
                │    MCT 卡模拟演进路线     │
                └─────────────┬─────────────┘
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
   [ 路线 A ]            [ 路线 B ]            [ 路线 C ]
 原生 Android HCE      外部模拟设备联动      系统特权与内核补丁
 (标准 ISO-DEP)       (Chameleon/Proxmark)    (Root / Xposed)
 ─────────────────    ──────────────────    ─────────────────
 适用: 自定义读卡器    适用: 绝大多数门禁场景 适用: 仅限极客极少机型
 优势: 纯机身无外设    优势: 协议拟真度极高   优势: 纯机身免外设
 局限: 无法模拟MFC    局限: 需携带外置硬件   局限: 极易崩溃变砖
 状态: 适合实验预研    状态: 当前最佳工程方案 状态: 坚决不予采纳
```

### 5.1 路线 A：原生 Android HCE 实验室模块 (纯机身探索)
- **技术定位**：在 MCT 中增加独立的 `HostApduService` 实验模块，面向自定义 ISO-DEP 读卡器；
- **优势**：纯机身运行，无需额外硬件；
- **局限**：**无法模拟 MIFARE Classic 物理门禁卡**；
- **评估**：可作为进阶协议测试工具，但无法解决刷实体门禁卡的核心诉求。

### 5.2 路线 B：外部模拟设备联动前端 (当前最成熟的工程路线)
- **技术定位**：将 MCT 作为高生产力的数据中心，通过 **BLE (低功耗蓝牙) 或 USB-OTG** 控制专业便携模拟设备（如 **ChameleonUltra / 变色龙 Ultra** 或 **ChameleonMini**）；
- **设备能力与客观局限性（纠偏）**：
  - **优势**：外设硬件内部配备专用高频射频芯片与定制固件，支持对 MIFARE Classic 1K/4K 各扇区密钥、UID、BCC 及特殊后门指令的高拟真模拟；
  - **客观局限性（非 100% 完美）**：
    1. **固件版本影响**：固件算法对 Crypto1 响应时序在特定版本可能存在微秒级偏差；
    2. **读卡器天线调谐与射频场强**：部分门禁读卡器天线发射功率较弱或载波频偏较严苛，微型外设在特定几何角度下可能出现耦合不良；
    3. **复杂协议与反克隆机制**：带滚动码（Rolling Code）、双向动态防伪算法或云端联机校验的复杂门禁系统，无法仅凭转储数据离线刷开；
    4. **外设限制**：用户出门需携带车钥匙大小的独立硬件；
  - **评估**：这是目前全行业在不破坏手机系统安全前提下，**成功率最高、最成熟的工程解决方案**。

### 5.3 路线 C：系统特权、Root 补丁与 NFC HAL 篡改 (坚决不予采纳)
- **技术定位**：借助 KernelSU / Magisk 模块，修改系统 `/system/etc/libnfc-nci.conf`、替换 NFC 驱动库；
- **致命缺陷**：不同机型芯片差异极大，极易引发 NFC 守护进程无限重启、异常耗电甚至手机无法开机；且绝大多数机型依然无法绕过 Crypto1 硬件缺失；
- **评估**：严重破坏设备安全性与稳定性，坚决不予采纳。

## 六、卡模拟安全、法律边界与长期目标保留

### 6.1 安全与法律合规红线
- 模拟技术仅限于用户拥有合法使用权与测试授权的门禁/考勤卡；
- 严禁尝试模拟银行卡、公共交通卡或涉及公共安全与财产安全的加密凭证；
- 任何卡模拟均不等于获得目标系统的准入授权。

### 6.2 长期技术愿景保留（不放弃纯机身方案）
- **外设方案是当前最可靠的工程桥梁，但不能直接画等号为手机原生模拟**；
- 用户希望“手机机身直接刷卡、无需随身携带外设”的需求完全合理且具有极高的体验价值；
- **本项目在当前阶段推荐采纳外设联动的同时，依然长期保留对手机原生/纯机身模拟方案的持续跟踪**（持续跟进 Android 未来版本对 NFC 权限与更底层硬件特权的开放动向，以及新一代硬件特性的演进），绝不关死纯机身卡模拟的探索方向。

## 七、P18 最终技术决策矩阵

| 决策维度 | 权威结论 | 依据与说明 |
| :--- | :--- | :--- |
| **A. 官方 HCE 可行性** | **有限可行 (仅限 ISO-DEP)** | 仅支持标准 APDU / NDEF，**无法用于 MIFARE Classic 物理卡片模拟**。 |
| **B. 原生 MFC 模拟可行性** | **当前普通 App 完全不可行** | 射频层 Crypto1 流密码、控制器微码路由及随机 UID 机制物理锁死。 |
| **C. 外设模拟兼容性评级** | **高拟真度 (需分别验证)** | ChameleonUltra 具备极高拟真度，但在特定固件、严苛读卡器与复杂协议下**必须分别实测验证，非绝对 100%**。 |
| **D. 推荐落地实施路线** | **以路线 B 为当前工程重点，同时保留纯机身模拟长期预研** | 当前优先规划通过 BLE/USB 与 ChameleonUltra 联动；长期持续关注纯机身免外设方案的技术突破。 |

### 下一步研发实施路线图
1. **P16/P17 当前收口**：交付 UI 2.0 冻结版 APK，等待用户人工实机体验；
2. **P18 进阶研发期**：
   - 阶段 1：调研 ChameleonUltra 官方开源 BLE 通讯协议接口；
